Project 01

Kafka 기반 분산 시스템 운영·관측·부하 검증

2025.05 – 2025.06  ·  개인 프로젝트  ·  GitHub

지표 기반의 워크로드 분석으로 컨슈머·파티션 배치 불균형을 발견하고, 분산 배치를 통해 응답 지연을 2.06s에서 33.3ms로 단축했습니다. 브로커 장애 실험으로 메시지 손실 없이 처리 흐름이 유지됨을 검증하고, 이후 EKS 배포와 CI/CD 파이프라인 구성까지 확장했습니다.

배경 및 목표

단순히 Kafka를 설치하고 메시지를 주고받는 수준을 넘어서, 실제 운영 환경처럼 분산 구성을 갖추고 그 위에서 시스템이 어떻게 동작하는지를 직접 관찰하고 싶었습니다.

특히 관측 가능성의 개념을 직접 경험해보는 것이 핵심 목표였습니다. 부하를 가하고, 지표를 보고, 문제를 찾고, 개선하는 사이클을 한 번 완성하는 것을 목표로 설정했습니다.

아키텍처 선택 — 트레이드오프

멀티 브로커 구성을 위해 AWS EC2(t3.medium) 3대를 선택했습니다. 브로커 간 통신, 리더 재선출, ISR 변화를 더 실제 운영 환경에 가깝게 관찰하기 위해 서로 다른 EC2 인스턴스에 브로커를 분산 배치했습니다.

모니터링 스택은 처음에 Prometheus로 구성했다가 VictoriaMetrics로 전환했습니다. 초기에는 Prometheus로 지표를 수집했지만, 이 프로젝트에서는 장기 저장보다 경량 수집과 원격 저장 구조가 더 중요하다고 판단했기에 수집은 vmagent, 저장은 VictoriaMetrics로 분리했습니다. vmagent가 Prometheus 스크래핑 설정을 그대로 사용할 수 있어 기존 exporter 생태계를 그대로 유지하면서 모니터링 구조를 단순화할 수 있다는 점도 함께 고려했습니다.

구현 내용

  • EC2 3대에 Docker Compose로 Kafka 멀티 브로커 클러스터 구축. 각 노드에 kafka-exporter, cAdvisor 배포
  • vmagent가 각 노드의 지표를 수집해 VictoriaMetrics로 전달, Grafana에서 Lag·Latency·컨테이너 리소스를 단일 대시보드로 통합
  • 쿠폰 발급 요청을 받은 Django API 서버가 Kafka에 메시지를 전송하고, 컨슈머 컨테이너 6개로 분산 처리 흐름 재현
  • k6로 5,000 / 10,000 / 15,000 / 18,000건 단계별 부하 테스트 진행. 싱글 브로커 → 멀티 브로커 전환 전후를 동일 조건(180초, 15,000건)에서 비교해 수치로 검증

문제 발견 → 분석 → 개선

1. 워크로드 편중 발견
멀티 브로커로 전환한 뒤 동일 조건으로 부하 테스트를 재실행했는데, 인프라를 확장했음에도 p95 응답 지연이 오히려 약 9.4배 증가했습니다. 자원과 메시지 처리 컨테이너를 늘렸는데도 성능이 떨어졌다는 점이 이상해 Grafana 대시보드를 점검했고, EC2 인스턴스 간 CPU 사용률 편차가 크다는 것을 발견했습니다. 특정 인스턴스가 78%까지 치솟는 동안 다른 인스턴스는 20% 수준에 머물렀습니다. 컨슈머 배치 현황을 확인하자 원인이 명확해졌습니다. 총 6개의 컨슈머 컨테이너가 모두 같은 EC2 인스턴스에 몰려 있었고, 파티션의 리더도 같은 브로커에 집중된 상태였습니다.

2. 분산 배치로 개선
각 EC2에 브로커 1개 + 컨슈머 2개씩 균등 배치하고, 파티션 리더도 분산되도록 조정했습니다. 이후 동일 조건으로 부하 테스트를 재실행하자 응답 지연(p95)이 2.06s에서 33.3ms로 단축됐고, 피크 CPU 사용률이 78% → 68%로 낮아졌습니다. 가장 부하가 높았던 컨테이너 기준으로는 약 47% 완화되었습니다.

3. 추가 병목 식별
분산 배치 이후에도 최대 부하 구간에서 응답 지연이 남아 있었습니다. 쿼리 실행 로그를 분석한 결과 MySQL I/O 비용이 병목임을 확인했습니다. 메시지 처리마다 DB 쓰기가 발생하는 구조였기 때문에, 컨슈머 처리량이 늘어날수록 DB가 따라오지 못하는 상황이었습니다. 서비스 확장 시, DB 전용 EC2 분리를 개선 방안으로 정리했습니다.

장애 내성 검증

부하 테스트 중 브로커 1대를 강제 종료해 장애 상황을 재현했습니다. 리더 재선출 과정과 ISR(In-Sync Replica) 변화를 실시간으로 관찰했고, 메시지 손실 없이 서비스가 지속됨을 확인했습니다. 테스트 전후 producer 발행 건수와 consumer 처리 완료 건수, DB 저장 건수를 비교해 누락 여부를 확인했습니다. 이 과정에서 acks=all, replication.factor=3, min.insync.replicas=2 설정이 실제로 어떻게 동작하는지 체감할 수 있었습니다.

구현 확장 - EKS 배포 및 CI/CD 구성

  • Docker Compose 기반 구성을 EKS로 전환. eksctl 명령으로 VPC, 서브넷, IAM 역할, EC2 워커 노드 2대가 포함된 Managed Node Group을 자동 구성.
  • Kafka 클러스터는 Strimzi Operator의 CR(Custom Resource)로 선언해 브로커 3대 배포. KafkaNodePool로 replicas를 관리하고, Strimzi가 StatefulSet·Service·PVC를 자동 생성.
  • 애플리케이션 코드는 수정 없이 환경변수만 교체. 서비스 간 통신 주소를 EC2 IP에서 K8s Service DNS로 변경하고 ConfigMap으로 분리.
  • GitHub Actions로 CI/CD 파이프라인 구축. 코드 변경 시 이미지 빌드 → GHCR push → EKS 자동 배포까지 실행.

Project 02

서버리스 비동기 파이프라인 IaC 구축과 운영

2025.03  ·  개인 프로젝트  ·  GitHub

이벤트 예약 시스템을 서버리스 비동기 파이프라인으로 설계하고 AWS CDK로 IaC를 구현했습니다. 콘솔에서 수동으로 설정한 구성을 코드로 전환하는 과정에서 코드와 실제 인프라가 불일치하는 문제를 정리하고, 배포·롤백·런타임·성능 전반에서 마주친 장애를 추적·해결했습니다. 더불어 NAT Gateway와 VPC Endpoint 두 네트워크 구성의 비용 구조를 비교해 최소 36% 절감 시나리오를 도출했습니다.

배경 및 목표

이벤트 예약 시스템은 평소와 피크 타임의 요청량 차이가 크다는 특성이 있습니다. 서버를 상시 운영하는 구조에서는 유휴 비용이 크고 피크 타임 확장성을 별도로 고려해야 하기 때문에, 트래픽에 따라 자동 확장되는 서버리스 자원을 선택했습니다.

구축에 그치지 않고, 만든 시스템을 코드로 일관되게 관리하고 운영 중 문제를 추적·해결하는 사이클을 경험하는 것을 목표로 삼았습니다. 인프라 전체를 AWS CDK로 정의하고, 배포·롤백·부하 상황에서 실제로 무엇이 어떻게 깨지는지를 직접 관찰하고자 했습니다.

아키텍처 설계

API Gateway → Lambda(예약 요청) → SQS FIFO → Lambda(예약 처리) → DynamoDB로 이어지는 비동기 파이프라인을 구성했습니다. 요청 수신과 실제 처리를 분리해 피크 트래픽을 큐로 흡수하고, Lambda 처리 실패 시 SQS 자동 재전달로 안정성을 확보했습니다.

  • SQS FIFO에서 좌석 기준으로 메시지 그룹을 분리해 동일 좌석 요청을 순차 처리
  • DynamoDB 조건부 쓰기(attribute_not_exists)로 재시도·중복 요청에도 좌석 중복 예약 방지
  • Lambda는 Private Subnet에 배치해 관리형 서비스 접근 경로를 네트워크 설계 대상으로 둠

NAT Gateway 기반 실제 구축 아키텍처 vs VPC Endpoint 기반 설계 아키텍처

IaC 구축 — 콘솔 설정을 코드 전환

전체 인프라를 AWS CDK로 Network, Application, Database, Storage, Monitoring, Compute 6개 스택으로 분리해 역할 기준으로 구성했습니다.

초기에는 일부 설정(Lambda의 VPC 연결, SQS Batch Size, Provisioned Concurrency용 alias)을 콘솔에서 수동으로 적용한 상태였습니다. 이 경우 cdk destroy 후 재배포 시 수동 설정이 사라지고, 코드와 실제 인프라가 불일치하는 문제가 발생합니다. 실제로 코드의 Batch Size와 콘솔 운영값이 다르게 설정돼 있는 것을 확인했고, 세 항목을 모두 CDK 코드로 이관해 인프라 상태를 코드만으로 재현할 수 있도록 정리했습니다.

운영 — 장애 추적 및 해결

구축·운영 과정에서 마주친 장애를 증상 → 원인 → 해결 → 재발 방지 형식으로 기록했습니다. 배포·롤백·런타임·성능 등 운영의 여러 단계에서 발생하는 서로 다른 성격의 문제들을 다뤘습니다.

1. 런타임 — 핸들러 모듈 로드 실패
배포 후 API가 500을 반환했고, CloudWatch 로그에서 Runtime.ImportModuleError를 확인했습니다. 배포 패키지를 열어보니 TypeScript 핸들러가 트랜스파일되지 않은 채 포함돼 있었습니다. Code.fromAsset이 디렉터리를 단순 압축만 한다는 점을 파악하고, esbuild로 빌드를 수행하는 NodejsFunction으로 전환해 빌드 단계를 IaC에 포함시켰습니다.

2. 롤백 — Lambda VPC ENI 의존성으로 인한 정체
배포 실패 후 롤백 과정에서 Security Group 삭제가 DELETE_FAILED로 약 30분간 멈췄습니다. Lambda를 VPC에 연결할 때 생성되는 ENI의 정리 지연이 원인이었고, CloudFormation이 ENI 해제 전에 SG 삭제를 시도하기 때문임을 확인했습니다. Lambda의 VPC 구성 변경은 배포뿐 아니라 롤백도 느리다는 점을 운영 전제로 정리했습니다.

3. 성능 — 부하 테스트로 콜드스타트 병목 정량화
Artillery로 초당 100 요청 부하 테스트를 수행한 결과, median 응답은 62ms로 안정적이나 p99는 975ms까지 상승했습니다. p95·p99 분포를 보면서 지연이 VPC 콜드스타트 구간에 집중된다는 것을 확인했고, 계정 동시성 한도 상향 후 Provisioned Concurrency 적용을 개선 방향으로 정리했습니다.

운영 - 비용 구조 점검과 개선안 도출

NAT Gateway로 구축 후 비용 구조를 점검하면서, Private Subnet의 Lambda가 SQS·SNS·DynamoDB 등 관리형 서비스에 접근하는 경로를 VPC Endpoint로 대체했을 떄의 비용을 비교 검토했습니다. AWS Pricing Calculator로 2-AZ 환경, 월 30만건 요청 기준으로 시뮬레이션했습니다.
